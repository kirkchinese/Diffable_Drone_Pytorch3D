# 视觉梯度截断问题调查报告

## 1. 问题描述

在训练循环 (`train.py` L632) 中，渲染深度图使用了 `torch.no_grad()`：
```python
with torch.no_grad():
    _, depth = self.env.render(...)
depth = depth.requires_grad_(False)
```
这意味着深度图**没有**从渲染器获得梯度反向传播路径。策略模型虽然从深度图中提取特征，
但梯度在"物理状态 → 渲染 → 深度图"这条链路上被截断。

本报告调查该设计是否为缺陷，以及是否可以修复。

## 2. 参考项目分析

参考项目 DiffPhysDrone 的渲染实现位于 `env_cuda.py, render_kernel.cu`。

### 2.1 渲染器实现

参考项目**未使用** PyTorch3D 或任何可微分渲染框架，而是自行实现了基于 CUDA 的光线投射内核：

```python
# env_cuda.py
img = torch.empty(B, H, W, device=device)  # 手动分配画布
render_kernel_launch(img, ...)              # 原始 CUDA kernel，无 autograd 包装
```

关键技术特征：
- `torch.empty()` 创建画布，无计算图
- 原始 CUDA 内核直接写入像素值，**不经过** `torch.autograd.Function`
- 渲染后对 depth 执行 `depth.clamp_()` **原地操作**，进一步证实无梯度意图

### 2.2 梯度路径设计

参考项目的梯度架构：

```
                    ┌─────────────────┐
  深度图 ─(无梯度)─→ │  策略网络 (CNN+GRU) │ ─→ 动作指令
                    └─────────────────┘
                            │
                            ▼ 梯度反传
                    ┌─────────────────┐
                    │  可微分物理引擎    │ ←─ 损失函数
                    │  (RunFunction     │
                    │   autograd.Function│
                    │   + CUDA backward) │
                    └─────────────────┘
```

- **可微分部分**：物理动力学（通过自定义 `autograd.Function` 实现 forward/backward CUDA 内核）
- **不可微分部分**：渲染（纯前向 CUDA 光线投射，无 backward 实现）

### 2.3 结论

**参考项目的渲染同样不可微分**。我们的 `torch.no_grad()` 与参考项目的行为**功能等价**。

## 3. 技术分析

### 3.1 为什么渲染不需要梯度

在"可微分物理 + 不可微分渲染"架构中，梯度流如下：

```
Loss ← 状态历史 (p, v) ← 物理引擎 step() ← 控制指令 ← 策略模型 ← 深度图(detach)
                              ↑
                          梯度反传到此
```

策略模型是"观测→动作"的映射器。深度图作为**观测输入**仅需要前向传播：
- 模型从深度图中提取空间特征（哪里有障碍物、距离多远）
- 梯度通过模型内部参数流动（CNN权重、GRU权重）
- 不需要"如果障碍物左移 1cm，深度图如何变化"这种渲染梯度

物理引擎处理所有与状态相关的梯度（位置/速度/姿态 → 下一时刻位置/速度/姿态）。

### 3.2 如果移除 `torch.no_grad()` 会怎样

PyTorch3D 的光栅化器在反向传播时可能产生**数值不稳定**问题：
- 透视投影的雅可比矩阵在近平面附近趋于奇异
- 遮挡边界处的梯度不连续
- 训练资源中的注释已记录："不这么做会导致梯度爆炸"

这正是参考项目选择不可微分渲染的原因之一。

### 3.3 能否替换为可微分渲染

理论上可行，但代价极大：

| 方案 | 可行性 | 代价 |
|------|--------|------|
| PyTorch3D SoftRasterizer | 中 | 需要处理数值不稳定，渲染速度显著下降 |
| NeRF 系列 | 低 | 完全重建场景表示，不兼容当前网格管线 |
| 3D Gaussian Splatting | 低 | 同上，需要重新设计场景表示 |
| 自定义可微光栅化 | 中 | 工程量大，需要手写 CUDA backward |

**所有方案都需要根本性的架构变更**，且收益不明确——参考项目已验证不可微分渲染在该任务上可行。

## 4. 最终结论

| 项目 | 渲染梯度 | 物理梯度 |
|------|----------|----------|
| 参考项目 (DiffPhysDrone) | ✗ 无（原始 CUDA 内核） | ✓ 有（autograd.Function） |
| 本项目 | ✗ 无（torch.no_grad） | ✓ 有（PyTorch autograd） |

**视觉梯度截断是设计意图，不是缺陷。** `torch.no_grad()` 的使用是正确的，与参考项目架构一致。
渲染在本框架中充当**传感器模拟**角色，不参与梯度计算。不建议修复。
