# 训练指南：框架分析与最佳实践

> 基于 `experiment/exp6_full_framework_overhaul` 分支的深度代码审查与性能分析。
> 硬件环境：GPU0 RTX 3080 (10GB)、GPU1 RTX 3060 (6GB)。

---

## 一、性能优化总结

### 1.1 关键修复：渲染器 extend 缓存失效（已合入）

**问题**：`_update_render_scene()` 在每帧渲染时无条件调用 `clear_dynamic_meshes()`，
导致 `_extended_mesh_cache` 被清空。后续 `render()` 被迫每帧重建 `mesh.extend(B)`
（将场景网格复制 B 份供批量渲染），产生了**占总耗时 95%** 的冗余开销。

**修复**：一行条件守卫——仅当渲染器确实持有动态网格时才执行清除。

**实测 (B=32, 48×64, depth-only, RTX 3080)**:

| 组件 | 修复前 | 修复后 | 提升 |
|------|--------|--------|------|
| Render | 276.73 ms (95%) | 12.98 ms (68%) | **21.3×** |
| KNN | 7.87 ms (3%) | 5.28 ms (28%) | 1.5× |
| Model | 4.74 ms (2%) | 0.24 ms (1%) | — |
| Total/step | 290 ms | 19.19 ms | **15.1×** |
| Episode (T=200) | 58.0 s | 3.8 s | **15.3×** |
| 50k iters | ~33.6 天 | ~2.2 天 | |

> KNN 和 Model 的提速是 GPU 不再被重复 extend 操作阻塞的连带效应。

### 1.2 各组件耗时分布（优化后）

```
Render:   12.98 ms  (68%)   ← 仍为最大瓶颈，但已在合理范围
KNN:       5.28 ms  (28%)   ← 50k 点云 × 10 子步 × B 查询
Model:     0.24 ms  ( 1%)   ← CNN+GRU 前向极轻
Dynamics:  0.69 ms  ( 4%)   ← Verlet 积分
```

### 1.3 多无人机渲染的 O(B²) 问题

使用 `drone_mesh_path` 启用无人机网格后，每组渲染需要：
- `set_dynamic_meshes()` → 缓存失效
- `join_meshes_as_scene()` → 合并静态场景 + N 架无人机网格
- `mesh.extend(G)` → 重建批量

| 配置 | B=16 | B=32 | B=48 |
|------|------|------|------|
| 单机模式 | 9.6 ms | 12.8 ms | 14.8 ms |
| 多机模式 (n_group=B) | 108.9 ms | 326.1 ms | 762.7 ms |
| 倍率 | 11× | 25× | **51×** |

**建议**：多机碰撞检测已通过 `inter_drone_distances()` 数学计算实现，
不依赖渲染。除非训练目标明确需要在深度图中"看到"其他无人机，
否则**不要**加载无人机网格（不传 `--drone_mesh_path`）。

### 1.4 其他效率要点

| 项目 | 现状 | 说明 |
|------|------|------|
| `render_interval=2` | 可选 | 隔帧渲染，深度不参与梯度，节省 ~50% 渲染时间 |
| `no_grad()` 渲染 | 已有 | 避免 PyTorch3D 透视投影反向传播的数值爆炸 |
| 截断 BPTT (每 30 步) | 已有 | 限制 GRU 梯度图长度，balance 记忆 vs 显存/稳定性 |
| `bin_size=0` | naive 光栅化 | 对 48×64 + 2 万面片场景已是最优选择 |
| `subdivide_times=0` | 已有 | 配合 `z_clip_value` 实现零质量损失，面片从 106 万→1.6 万 |

## 二、框架理论缺陷分析

### 缺陷 1：渲染管线零梯度 [严重程度: ★★★★☆]

深度图渲染在 `torch.no_grad()` 内执行，**模型无法通过视觉路径获得梯度信号**。
唯一的梯度通道是：动力学 p,v → KNN 距离 → 损失。

**影响**：模型不能学到"去某个位置可以看到更多/更少信息"这类视觉驱动的行为。
避障完全依赖 KNN 距离的梯度信号（"你离障碍物近了，请后退"），
而非深度图呈现的空间结构。

**缓解**：这是有意为之——PyTorch3D 透视投影的反向传播存在严重数值问题。
如需引入视觉梯度，需改用 NeRF/3DGS 风格的可微渲染器或 SDF-based renderer。

### 缺陷 2：速度分解损失不惩罚绕远 [严重程度: ★★★☆☆]

当前的 velocity decomposition loss 只惩罚前向速度不足 (`shortfall = relu(target_speed - v_fwd)`)，
横向分量完全免罚。

```
v=0:       loss = smooth_l1(target_speed)    ← 静止被惩罚
v=横向:    loss = smooth_l1(target_speed)    ← 与静止相同
v=45°绕行: loss = smooth_l1(ts - ||v||cos45°) ← 比静止好
v=满速前进: loss ≈ 0                          ← 最优
```

**结果**：一架以 V 速度绕大圈的无人机，其前向分量仍为正（`v_fwd = V×cosθ > 0`），
损失只要 `v_fwd ≥ target_speed` 就为零。模型可能学到**沿切线方向持续发散**的绕行策略。

**建议**：在训练后期（>10k iter）添加微弱的 `coef_lateral=0.05~0.1`，
或加入路径效率指标（实际位移/总行程距离），惩罚不必要的横向运动。

### 缺陷 3：GRU 隐状态冷启动 [严重程度: ★★☆☆☆]

每个 episode `h` 初始化为 `None`（零向量）。模型在前 10-20 步处于"盲飞"状态，
因为 GRU 尚未积累足够的时序上下文。

**影响**：
- 初始帧的避障反应滞后，可能产生碰撞
- 模型可能隐式学到"前几帧不做大动作"的保守策略

**建议**：视效果考虑在 `model.reset()` 中用可学习的 `h_init` 替代零初始化。
或在 episode 开始前提供 3-5 帧"预热渲染"但不计入损失。

### 缺陷 4：Model_adaptive 对训练分辨率过度下采样 [严重程度: ★★☆☆☆]

Model_adaptive 有 5 层 stride=2 卷积（总下采样 32×）：
```
48×64 → 24×32 → 12×16 → 6×8 → 3×4 → 2×2
```
然后 `AdaptiveAvgPool2d((4,6))` 将 2×2 **上采样**到 4×6。
这等于先过度压缩信息再"插值还原"，是一种信息损失。

**对比 Model_bigger**（4 层，专为 48×64 设计）：
```
48×64 → 24×32 → 12×16 → 6×8 → 3×4  (直接 flatten)
```

**影响**：训练分辨率下 Model_adaptive 不如 Model_bigger 高效。
但 Model_adaptive 的设计目标是支持任意分辨率（训练 48×64，部署 640×480），
所以这是有意的设计取舍。

**建议**：如果确定只在 48×64 训练和部署，优先使用 Model_bigger（更高效且参数更少）。
如需多分辨率支持，当前设计已足够，但可考虑减少到 4 层 conv + adaptive pool。

### 缺陷 5：无人机间碰撞梯度信号太弱 [严重程度: ★★★☆☆]

碰撞损失使用 `softplus(-32 × d)`。当 d > 0（未碰撞）时：

| 间距 d | softplus(-32d) | 梯度 d(loss)/dd |
|--------|---------------|-----------------|
| 0.3 m  | 1.5e-4       | ~0              |
| 0.1 m  | 0.04         | ~1.3            |
| 0.05 m | 0.27         | ~10             |
| 0.0 m  | 0.69         | ~16             |

在 d=0.1m（10cm 间距）时梯度信号已非常微弱。如果无人机飞行速度 3m/s，
单步 67ms 移动 0.2m，可能从"安全距离"直接跳入碰撞区而来不及产生足够梯度。

**建议**：将系数从 -32 降低到 -16 或 -8，扩大激活区域。
或改用 `barrier(x) = 1/x` 式的障碍函数，在中距离就开始产生排斥梯度。

### 缺陷 6：相机深度噪声不足以弥合 Sim-Real Gap [严重程度: ★★☆☆☆]

`noise_std=0.02` 加在变换后的深度值 `3.0/z - 0.6` 上。
对于 z=1m 的障碍物，变换后值为 2.4，噪声 ±0.02 等效深度偏差 ±0.003m (3mm)。
真实深度传感器（Realsense D435 等）在 1m 处的噪声为 ±5-10mm，且存在系统性孔洞和飞溅噪声。

**建议**：
1. 增大 `noise_std` 至 0.05-0.1
2. 添加随机像素 dropout（模拟深度传感器孔洞）
3. 添加 depth dilation/erosion 随机形态学操作

### 缺陷 7：最大速度范围可能过宽 [严重程度: ★★☆☆☆]

`max_speed = 0.75 + 5 * rand` → [0.75, 5.75] m/s。
在密集障碍场景中，5.75 m/s 对应 0.38m/step 的位移，
超过典型安全边距 0.3-0.8m 的相当比例。

**建议**：根据障碍场景密度分阶段训练：
- Phase 1 (0-10k): max_speed ∈ [0.75, 3.0] — 低速学避障
- Phase 2 (10k-30k): max_speed ∈ [0.75, 5.0] — 提速
- Phase 3 (30k-50k): max_speed ∈ [0.75, 5.75] — 全速

### 缺陷 8：窗口平均可能模糊时序信号 [严重程度: ★☆☆☆☆]

`window_size=30` 步滑动平均 ≈ 2 秒。快速的避障动作（瞬间减速+偏转+加速）
在 2 秒窗口内被严重平滑，可能导致模型学到过于保守的行为。

**建议**：保持 window_size=30 以稳定训练初期，但可试验 window_size=15。

## 三、最优训练参数与完整命令

### 3.1 推荐配置（单机避障，最大化 RTX 3080 利用率）

基于性能分析推导的关键参数选择理据：

| 参数 | 推荐值 | 理据 |
|------|--------|------|
| batch_size | **48** | B=48 单步 ~22ms（包含 render_interval=2），VRAM ~4.5GB，留余量 |
| timesteps | **200** | T=200 提供 13.3s 轨迹（15Hz），足够穿越 16m 场景 |
| render_interval | **2** | 隔帧渲染，深度不参与梯度，不影响训练质量，省 34% 总时间 |
| lr | **5e-4** | AdamW + CosineAnnealing，eta_min=5e-6 |
| num_iters | **50000** | Est 2.2s/iter → ~30h 完成 |
| grad_decay | **0.4** | 参考项目验证值，控制长时梯度衰减 |
| coef_collide | **3.0** | 略高于默认 2.0，强化碰撞惩罚 |
| coef_obj_avoidance | **2.0** | 略高于默认 1.5，barrier 函数更积极 |
| coef_ground_affinity | **0.1** | 防止飞高规避（high-altitude exploitation） |
| num_obstacles | **25-50** | 中等密度，平衡训练难度和渲染开销 |
| spawn_z_max | **3.0** | 限制高度，配合 ground_affinity 形成有效约束 |
| n_drones_per_group | **1** | 单机模式（无需 drone_mesh），渲染最快 |

## 四、训练团队建议

### 4.1 训练策略

1. **优先使用 `render_interval=2`**：深度图不参与梯度，隔帧复用质量损失极小
   （@15Hz 控制频率，66ms 的深度延迟在正常飞行速度下影响可忽略）。

2. **监控 `ar` 和 `task_score` 指标**：
   - `ar = success_rate × avg_speed`：安全且快速
   - `task_score = collision_free × progress × avg_speed`：综合任务质量
   - 最佳模型自动按这两个指标保存（`best_ar.pth`、`best_task_score.pth`）

3. **场景复杂度递进**：
   - 初期 (0-5k)：20-30 障碍物，关注 loss 是否正常收敛
   - 中期 (5k-25k)：30-50 障碍物，观察 collision_free_rate 是否上升
   - 后期 (25k+)：可增至 40-60 障碍物提高泛化，或切换多机模式

4. **Checkpoint 恢复**：v2 格式自动恢复 optimizer/scheduler 状态并 diff 超参差异。
   恢复训练时无需手动对齐学习率。

### 4.2 常见问题排查

| 现象 | 可能原因 | 处置 |
|------|----------|------|
| loss NaN | 学习率过高 / grad_decay 过大 | 降 lr 至 1e-4，grad_decay 至 0.3 |
| success_rate 始终为 0 | 障碍物过密 / spawn_z_max 过低 | 减少 num_obstacles，升高 spawn_z_max |
| 高 avg_speed 但低 collision_free | 碰撞惩罩不够 | 加大 coef_collide 至 5.0 |
| 低 avg_speed 高 collision_free | 模型过于保守 | 降低 coef_obj_avoidance，增加 coef_v |
| OOM | batch_size 过大 | 降至 32-48，或增加 render_interval |
| 速度不提升 | window_size 平滑过度 | 试 window_size=15 |

### 4.3 评估与可视化

```bash
# 单机评估 (GPU1 不干扰训练)
conda run -n pytorch python visualize_eval.py \
    --checkpoint ./checkpoints/adaptive_optimal_run/best_task_score.pth \
    --num_episodes 32 \
    --random_scene \
    --gpu 1

# TensorBoard 实时监控
tensorboard --logdir ./logs --bind_all
```

### 4.4 关键架构限制（不可通过调参解决）

1. **无视觉梯度**：模型学不到"主动探索"行为，只能被动避障
2. **串行时步**：GRU 隐状态依赖使得 T 个时步无法并行，训练速度 ∝ 1/T
3. **PyTorch3D 光栅化开销**：即使优化后仍占 68% 时间，是框架的硬性底线
4. **per-group 渲染无法合批**：每组场景不同，无法利用 batch rendering 的 extend 机制
